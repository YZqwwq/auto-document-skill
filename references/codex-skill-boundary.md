# Codex Skill 边界说明

这份说明用于明确 `auto-document` 的能力边界，避免后续维护者把它误解成“脚本内部自带 AI 调用”的项目。

## 一句话边界

`auto-document` 是一个面向 Codex 的项目理解与文档维护 skill。

它负责让**当前会话中的 Codex**按既定工作流理解项目、判断功能域、规划维护层级并落盘写文档；它**不负责**让 Python 脚本在脱离 Codex 的情况下自行完成模型推断。

## 谁负责什么

### 当前会话中的 Codex 负责

- 阅读 `SKILL.md` 与 `references/` 中的工作流约束
- 基于 summary、代码证据和上下文做功能域判断
- 决定当前应该更新 summary、structure 还是 modules
- 撰写和修改最终 markdown 文档内容
- 在必要时直接编辑仓库文件

### 仓库脚本负责

- 扫描仓库、整理路径事实和证据摘要
- 生成供 Codex 使用的推断协议、判断提示和占位结构
- 维护 `index.json`、`history/` 和文档目录骨架
- 在维护模式下整理 git 范围快照与建议动作

## 当前项目明确不负责什么

- 不负责在脚本内部自动调用模型
- 不负责提供独立于 Codex 的 AI provider 层
- 不负责把 placeholder 或 draft 结构冒充成最终语义结论
- 不负责在用户未触发 skill 时后台自动巡检或自动改写文档

## 如何理解“AI”

在这个项目里，如果文档提到“AI 协助判断”或“AI 生成草案”，默认都应理解为：

**当前正在使用这个 skill 的 Codex 会话。**

它不应被理解为：

- 某个脚本内部的隐藏模型调用
- 某个默认存在的外部 API
- 一个脱离 Codex 仍然能独立运转的自动推断器

## 占位结构的意义

项目中的一些脚本会生成：

- 功能域占位结果
- 结构层草案
- 维护建议
- judgment prompt

这些内容的定位是：

- 为当前会话中的 Codex 提供可复用的中间材料
- 帮助后续文档生成、维护和收敛更稳定

这些内容**不是**最终语义判断本身。

如果脚本里出现了看起来像“已经完成了功能域推断”的对象，维护时应优先检查：

- 它是不是只是协议或 placeholder
- 它有没有被误写成最终结论
- 它的命名、注释和输出文案是否足够诚实

## 设计上的直接后果

既然这个项目只需要适配 Codex，那么后续设计应优先强化：

- `evidence package`
- `prompt / judgment protocol`
- `summary -> structure -> modules` 的工作流约束
- `git awareness -> maintenance suggestion` 的范围整理

而不是优先强化：

- 脚本内模型调用
- provider 抽象层
- 脱离 Codex 的自动推断执行链

## 维护时的检查清单

后续审这个项目时，优先检查下面几个问题：

- 某个脚本是不是在假装自己已经完成了语义判断
- 某个 placeholder / draft / suggestion 是否被写成了最终结论
- 某个文档是否把“Codex 会话能力”误写成“脚本自动能力”
- 某个新设计是否在偷偷把项目往“脱离 Codex 的自动 AI 系统”方向带

只要以上问题持续被压住，这个项目的定位就会保持稳定。
