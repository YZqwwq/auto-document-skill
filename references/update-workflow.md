# 更新工作流

这份说明定义在当前项目定位下，`auto-document` 应如何进行日常维护与收敛。

新的默认原则不是“检测到代码变化就重写文档”，而是：

- 只有用户要求使用 skill 时，才进入维护
- 先判断变化是否影响文档语义
- 再决定是局部更新、向上收敛、要求人工复核，还是只更新 git 基线

## 工作流主线

新的维护顺序应理解为：

1. `project-summary.md`
2. 功能树与代码树映射
3. `modules/`

维护时必须先判断本次变化影响的是哪一层，再决定是否继续向下游扩散。

## 首先判断什么

### 1. 是否真的要改正文

变化发生后，第一判断不是“改哪篇文档”，而是：

当前文档描述是否已经失效。

如果答案是否定的：

- 不改正文
- 只更新 git 对齐点
- 把这次处理视为 `git_alignment_only`
- 清空 `pending_updates`
- 在 `module_state.last_update_strategy` 和 `history/change-log.md` 中留下本轮处理痕迹

### 2. 是否需要人工复核

当变化已经触及项目定位、核心设计理念或主要功能边界时，不应让 Codex 或脚本直接固化新解释，而应要求用户复核。

常见信号：

- 根级 README 被大幅改写
- 根级关键配置或启动方式发生根本变化
- 出现新的顶层系统面
- 项目从一种产品形态切到另一种产品形态
- 原有功能树已明显失真

一旦重新打开 summary 审查，下游功能树映射和模块文档默认进入 `stale`。

### 3. 本轮应落在哪一层

当确定“确实需要改正文”后，不再按“每个变化路径各自列文档”来处理，
而是先回答：

- 这次维护的主层级是 `summary`、`structure` 还是 `module`
- 当前是否需要先上卷，而不是直接补模块
- 当前 `pending_updates` 应该保存“待执行计划”，还是本轮已经完成无需待办

当前实现中，维护入口会把判断结果收敛为四类策略：

- `git_alignment_only`
  变化没有让正文语义失效，只更新 git 基线
- `content_update`
  变化集中在有限功能域内，按最小受影响功能域规划正文更新
- `reconcile`
  变化已经跨层或映射失真，应先上卷到结构层收敛
- `user_review_required`
  变化已经触及项目级意图或主要边界，应先让用户复核

无论最后收敛到哪一种策略，维护计划都应显式保留两类上下文：

- 证据摘要
  说明这次判断主要依据了哪些路径、边界信号、映射命中结果或未覆盖路径
- judgment prompt
  说明当前会话中的 Codex 在继续维护时应如何基于这些证据判断是正文更新、上卷收敛还是人工复核

补充语义：

- 这里的脚本负责整理变更证据、维护状态和生成判断提示
- 真正的维护层级判断由当前会话中的 Codex 完成，而不是由脚本内部自动拍板

## 分层判断规则

### 重新校准 summary

当项目级定位、服务目标、稳定架构理念发生变化时，优先重新校准 `overview/project-summary.md`。

典型情况：

- 项目当前状态和未来方向的描述已明显过时
- 新功能不是原有功能树上的自然扩展，而是新的系统面
- 用户明确要求调整项目级设计表达

### 更新功能树与代码树映射

当功能边界或代码落点关系变化时，更新 `overview/project-structure.md`。

典型情况：

- 顶层目录新增、删除或重命名
- 一个功能域被拆成多个下级功能域
- 某一功能的主要入口被迁移到其他路径
- 新增或删除文件已经改变了功能到代码的映射关系
- 当前变化没有命中已登记功能域，说明现有映射已无法稳定解释这些路径

### 更新模块文档

当变化停留在某个已登记功能域内部，且没有改动上层功能边界时，优先更新对应模块文档。

典型情况：

- 某个功能域内部实现细节发生变化
- 关键入口文件变化，导致阅读顺序需要调整
- 上下级功能关系未变，但下层实现说明已过时

在当前实现里：

- 模块级维护计划会优先只指向最小受影响功能域文档
- 不默认附带 `overview/project-structure.md`
- 只有当映射判断也失效时，才上卷到 `structure`

### 什么时候不上来就“同时更新映射和模块”

当前实现已经不再把“可能同时受影响”简单翻译成“同时列多篇文档”。

新的原则是：

- 先确定本轮主层级
- 再只保留这一层真正待执行的计划

因此：

- 如果需要结构层收敛，`pending_updates` 会优先收敛为结构层计划
- 如果需要 summary 复核，`pending_updates` 会进一步收敛为 summary 层计划
- 只有在真正进入正文执行阶段时，才继续向下游扩散

## 中小规模变更的维护顺序

1. 由用户触发 skill。
2. 读取 `project-docs/index.json`。
3. 检查当前是否存在可用 git。
4. 比较 `git_state.aligned_head_sha` 与当前 `HEAD`。
5. 汇总发生变化的文件。
6. 判断本次变化是否只需要更新 git 基线。
7. 如果需要改正文，再判断影响的是：
   - summary
   - 功能树与代码树映射
   - 具体功能模块
8. 把本轮结果收敛成一种明确策略：
   - `git_alignment_only`
   - `content_update`
   - `reconcile`
   - `user_review_required`
9. 只更新最小受影响功能模块；必要时向上收敛。
10. 把本轮证据摘要、判断提示和范围快照一起写入 `pending_updates`。
11. 更新状态字段和 git 基线。

## 新增或删除文件时的规则

新增或删除文件时，默认不能只补一篇模块文档。
至少需要同时检查：

- 功能树是否需要调整
- 代码树映射是否需要调整
- 对应模块文档是否需要调整

如果新增或删除的文件没有改变文档原有语义，可以保留正文不动，但仍要更新代码映射与 git 基线。

补充：

- 如果新增或删除的是测试、夹具或其他低语义风险路径，允许直接判定为 `git_alignment_only`
- 如果新增或删除后已经无法稳定映射到现有功能域，应优先进入 `reconcile`
- 如果新增或删除触及根级入口或关键配置，应优先进入 `user_review_required`

## 大范围变化时的收敛顺序

当发生以下情况时，优先执行收敛，而不是逐项补丁：

- 多个功能域同时被删改
- 顶层目录结构变化明显
- 原有功能树已经难以解释当前代码
- 文档与代码落点关系普遍失真
- 用户明确要求重划功能分支

推荐顺序：

1. 先判断 summary 是否仍成立。
2. 如果 summary 不成立，先回到 summary 校准阶段。
3. 如果 summary 仍成立，重建功能树与代码树映射。
4. 删除已经失效的功能文档。
5. 重写当前仍有效功能域的文档。
6. 重建 `modules/README.md`。
7. 更新 `index.json` 中的功能域、映射、状态和 git 字段。
8. 清空 `pending_updates`，因为系统已经重新对齐。

当前实现中的收敛结果还会额外体现为：

- `module_state.last_update_strategy = reconcile`
- `git_state.aligned_*` 被刷新到当前代码状态

## 人工驱动优先原则

- 维护模式由用户触发，不是自动巡检触发
- 用户可以要求删除某个功能分支、增加某个功能分支，或保留与当前代码树暂时不一致的文档
- 当用户意图与当前代码树不一致时，应先确认这是否是有效设计，而不是直接用代码覆盖文档

## 意图基线优先原则

- `project-summary.md` 一旦被视为可继续基线，就成为下游功能树和模块文档的认知起点
- 代码本身不能替代“项目希望成为什么”的信息
- 如果项目仍在演进中，summary 应显式区分：
  - 当前实现
  - 长期方向
- 当两者发生偏移时，不应直接让 Codex 或脚本用当前代码覆盖掉原有项目意图

## git 感知优先原则

- 如果项目存在 git，优先以 `aligned_head_sha` 作为正文对齐基线
- 当前 `HEAD` 领先于对齐点时，根据提交差异与工作区差异判断是否需要正文更新
- 当前 `HEAD` 落后于对齐点时，默认不自动回写文档
- 当前 `HEAD` 与对齐点分叉时，优先重新评估变化范围，必要时直接收敛
- 如果项目没有 git，当前不进入这套 skill 工作流

补充：

- 根级配置文件不会再被提前过滤掉，而是作为 summary / 上卷判断的重要信号
- `git_alignment_only` 是维护结果，不是“忽略本轮变化”
- 当脚本已经完成 `git_alignment_only` 处理后，索引里通常不会留下待处理项

## 实用启发式规则

- 如果 `README.md`、`package.json`、`pyproject.toml`、`Cargo.toml` 这类根级文件变化明显，优先检查 summary 是否仍成立
- 如果顶层目录变化，优先检查功能树与代码树映射
- 如果变更路径已经映射到某个功能域，优先更新该功能域文档
- 如果变化只影响实现细节，但不影响文档原有语义，优先只更新 git 基线
- 如果同一变化影响多个兄弟功能域，优先向上层功能收敛，而不是分别打补丁
- 如果变化只集中在测试、夹具、快照等低语义风险路径，优先判定为 `git_alignment_only`
- 如果变化命中了功能域内的入口或边界文件，优先规划最小功能域正文更新
