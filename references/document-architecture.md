# 文档架构

使用分层文档系统，而不是把文档堆成一堆扁平笔记。

## 设计原则

- 为整个文档系统创建一个根入口文档。
- 创建一个机器可读索引，让后续运行知道哪些内容已经存在。
- 把全局导航文档和聚焦子系统文档拆开。
- 把“当前实现真相”和 backlog 或推测性设计分开。
- 让功能树成为文档主骨架，代码路径只作为功能映射与阅读入口。
- 让脚本负责准备证据包、推断协议和状态，而由当前会话中的 Codex 完成语义判断。

## 推荐职责划分

### `README.md`

把它作为文档根目录的人类导航页。

应包含：

- 这个文档根目录是做什么的
- 应该怎么阅读
- 总览文档和模块文档分别放在哪里

### `index.json`

把它作为机器导航页。

应存储：

- skill 与 schema 版本
- 是否已经完成初始化
- 当前分析阶段
- 已生成的文档
- 项目路径与模块文档之间的映射关系
- 待处理的文档更新项

### `overview/`

用于第一轮项目理解。

常见文件：

- `project-summary.md`
- `project-structure.md`

这些文件应帮助新接手的人回答：

- 这个项目是做什么的
- 顶层功能域如何划分
- 下一步该读哪里

### `modules/`

用于功能域级的聚焦文档。

每个文件应解释一个功能域或稳定子系统：

- 职责
- 边界
- 关键文件
- 依赖关系
- 更新触发条件

### `history/`

用于操作过程的可追踪记录。

- `analysis-log.md` 记录分析轮次
- `change-log.md` 记录更新规划与文档维护工作

## 从整体到细节的推进方式

### 第一轮

产出：

- 一份简短的项目摘要
- 一份功能树到代码树的顶层映射草案
- 一份供当前会话中的 Codex 继续下钻的证据与协议集合

### 第二轮

产出：

- 每个重要功能域或稳定子系统对应一份文档
- 在 `modules/README.md` 中提供导航链接
- 在 `index.json` 中记录功能域到文档的映射，以及相关代码路径映射

### 增量更新

在代码变更后：

- 更新拥有该变更路径的模块文档
- 只有当整体结构或项目叙事发生变化时才更新总览文档
- 追加简短维护记录，而不是悄悄重写历史

## 反模式

- 不要每次运行都重新创建默认骨架。
- 不要把 backlog 当成当前实现真相。
- 不要把无关子系统混进一个巨大的 markdown 文件。
- 不要因为一个模块变化就重写全部文档。
- 不要让文档漂移而不记录变更内容和原因。
