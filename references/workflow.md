# auto-document 工作流

## 总原则

这个 skill 只提供一个自动化能力：初始化最小文档工作区。

正式项目文档由 agent 在当前会话中阅读、判断、询问用户并逐步写入。agent 不应依赖固定模板批量生成文档，也不应把目录名直接当成功能模块。

这里默认是 AI 在阅读项目，不是机器在执行状态机。进度记录应是白话、集中、可继续接手的阅读笔记。

`index.md` 只保留最近一次阅读记录，不维护完整历史日志。每次继续阅读时，agent 应覆盖“最近一次阅读记录”，同时更新“当前阅读进度”，避免索引无限变长。

## 新项目流程

### 1. 请求项目用途说明

在初始化前，先要求用户用一句话简单说明这个项目的用途。

要求：

- 不超过 200 字
- 说明项目整体方向
- 可以很粗略，例如“这是一个代码编辑器项目”或“这是一个 Electron 世界观编辑器”

如果用户没有提供，先不要初始化正式文档。

### 2. 初始化文档工作区

初始化只创建：

```text
project-docs/
├── index.md
├── project-description.md
└── document/
```

初始化时：

- 将项目用途写入 `project-description.md`
- 在 `index.md` 记录当前 git 状态
- 创建空的 `document/` 文件夹
- 不生成模块规划模板
- 不生成 summary、structure、modules 等旧式占位文档

### 3. 浅层阅读项目

初始化后，agent 先浅层阅读项目：

- 根目录文件
- README 或已有文档
- package / config / 构建入口
- 主要源码入口
- 用户明确提到的设计文档

目标是形成“可能的大功能模块”列表，而不是直接写正式文档。

### 4. 提出大功能模块并请求确认

agent 按自己的初步理解列出项目的大功能模块。

示例：

- 编辑模块
- AI Agent 模块
- 文件系统模块
- 渲染界面模块

列出后必须请求用户确认：

- 模块是否正确
- 是否需要合并、拆分或改名
- 是否遗漏重要功能模块

用户确认前，不进入正式深入文档阶段。

### 5. 建立大功能模块目录

用户确认后，在 `document/` 下按大功能模块建立目录。

每个大功能模块目录至少包含：

```text
document/
└── <module-name>/
    └── catalog.md
```

`catalog.md` 应保持干净，只列子功能模块。

推荐写法：

```md
# 编辑模块

## 子功能模块

- 待阅读后补充
```

不要在 `catalog.md` 里记录阅读任务、任务状态、进度日志或大段解释。阅读进度统一写入 `index.md`。

### 6. 按功能模块逐个深入阅读

agent 一次只深入一个大功能模块。

深入时应：

- 从用户确认的大模块边界出发
- 阅读相关代码、已有文档和调用链
- 按自己的理解拆出小功能模块
- 判断每个小功能模块应写成文件还是继续写成文件夹

例如：

```text
document/
└── editor/
    ├── catalog.md
    ├── file-lazy-loading.md
    ├── file-editing.md
    └── syntax-highlight/
        ├── catalog.md
        └── tokenizer.md
```

### 7. 小功能模块继续细分

如果 agent 认为某个小功能模块仍然过大，可以继续拆成文件夹。

拆分条件：

- 它包含多个独立职责
- 它有明显的多条调用链
- 它需要多篇文档才能讲清楚
- 它和其他子功能有稳定边界

不需要拆分的内容保持为单个 `.md` 文件。

### 8. 完成所有功能模块

agent 按用户确认的大功能模块逐个完成文档。

完成一个模块后，应更新：

- 该模块的 `catalog.md`
- `index.md` 的当前阅读进度和最近一次阅读记录
- 必要时记录 git 对齐状态

`index.md` 应用白话写清楚：

- 已经确认了哪些大功能模块
- 当前读到哪个模块
- 已经读了哪些关键路径
- 形成了哪些子功能判断
- 还有哪些问题要继续读
- 最近一次记录对应哪个 git 提交

## 已有项目流程

如果目标项目已经存在 `project-docs/index.md`：

1. 读取 `index.md`
2. 读取上次记录的 git 状态和阅读进度
3. 对比当前 git 状态
4. 判断哪些文档可能需要重新阅读
5. 按受影响的功能模块继续阅读和更新文档

如果 git 状态无法比较：

- 不直接覆盖旧文档
- 先阅读现有 `document/`
- 再向用户说明当前无法基于 git 判断增量范围

## index.md 的阅读记录方式

`index.md` 是单层阅读进度板，不做复杂嵌套结构，也不做完整历史日志。

重要规则：

- 只保留最近一次阅读记录
- 不追加多个日期小节
- 每轮继续阅读时直接覆盖旧的最近一次记录
- 历史事实如果已经沉淀成正式模块文档，不再留在 `index.md`

推荐长期保持这些区域：

```md
# 项目文档索引

## 项目用途

见 `project-description.md`。

## 最近 git 记录

- 分支：
- 提交：
- 工作区：
- 记录时间：

## 当前阅读进度

已经完成：
- 已初始化文档工作区。

接下来：
- 等待浅层阅读项目后提出大功能模块。

## 大功能模块

- 待确认

## 最近一次阅读记录

### 2026-07-15

已经干了什么：
- ...

还要干什么：
- ...

当前判断：
- ...

记录规则：
- 这里以后只保留最近一次阅读记录，不继续追加历史记录。
```

这里可以有少量 JSON fenced block 保存 git 原始信息，但不要把整体流程变成 JSON 状态机。

## 写作规则

- 文档必须来自实际阅读和理解
- 可以记录不确定问题，但不要把猜测写成事实
- 优先解释功能边界、关键入口和代码关系
- 不需要让所有文档拥有相同章节
- 大功能模块用文件夹组织
- 小功能模块可以是文件，也可以继续拆成文件夹
- `catalog.md` 只做子功能模块目录
- 阅读进度、阅读任务和判断轨迹只写在 `index.md`
- 如果代码和旧文档冲突，以代码为当前实现真相，再更新文档

## 禁止行为

- 初始化时批量生成模块模板
- 用目录树直接替代功能模块划分
- 用户确认前创建正式功能模块文档
- 为了填满章节而写重复格式内容
- 在未阅读相关代码前写实现结论
- 将未来计划和当前实现混写为同一事实
- 把阅读进度拆散到多个机器状态字段里
