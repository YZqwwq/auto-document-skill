# 文档写作规范

这份规范用于约束 `project-docs/` 下的文档写法，让人和当前会话中的 Codex 都能更快建立当前项目理解。

## 总原则

- 先给结论，再展开细节。
- 先说明“这个文档解决什么阅读问题”，再进入正文。
- 一份文档只解释一个层级的问题，不把多个层级混在一起。
- 优先描述当前状态，不解释设计演化历史。
- 让读者能快速回答：这是什么、为什么存在、应该先读哪里、改哪里时要更新它。
- 优先写项目理念、运行时实现、模块边界与阅读路径，不把工具链配置当成正文重点。
- 框架或技术栈只做轻量背景说明，例如 `Electron`、`Vue 3`，不要把 `tsconfig`、构建脚本或 lint 配置展开成主叙事。

## 推荐分块方式

### 总览类文档

适用于：

- `overview/project-summary.md`
- `overview/project-structure.md`

推荐结构：

1. 一句话定位
2. 这份文档回答什么问题
3. 核心结论
4. 阅读入口或推荐阅读顺序
5. 细节展开
6. 当前真相来源

### 模块类文档

适用于：

- `modules/*.md`

推荐结构：

1. 一句话定位
2. 范围
3. 这个功能域解决什么问题
4. 内部结构速览
5. 按问题找文档或目录
6. 关键文件或目录
7. 运行时边界
8. 与其他模块的关系
9. 当前维护原则
10. 阅读建议
11. 何时更新本文件

### 导航类文档

适用于：

- `project-docs/README.md`
- `modules/README.md`

推荐结构：

1. 这个目录是做什么的
2. 建议阅读顺序
3. 当前文档清单
4. 进入下一层的方式

## 每个分块应该怎么写

### 一句话定位

放在最前面，用 1 到 2 句话说明：

- 这个文档或模块是什么
- 它在整个项目中的角色是什么

### 这份文档回答什么问题

明确这份文档覆盖什么、不覆盖什么。

这样 Codex 和人都能知道：

- 应不应该继续读
- 什么时候该跳去别的文档

### 核心结论

把最重要的判断提前写出来，不要把关键信息埋在后面。

适合写：

- 当前系统边界
- 模块主要职责
- 当前推荐阅读路径

### 内部结构速览

不要一上来堆完整目录树。优先先总结结构，再列关键目录。

好写法：

- `src/` 主要分成 `main / preload / renderer / share`
- `developmentlog/` 主要分成“当前真相”“专题设计”“项目待办”

### 关键文件或目录

只列对理解有帮助的入口，不要把所有文件都列出来。

优先列：

- 入口文件
- 目录导航文件
- 承担边界职责的文件
- 容易误读的关键路径

### 运行时边界

模块文档里要明确：

- 哪些内容属于这个模块
- 哪些内容不属于这个模块
- 它和相邻模块的边界在哪里

### 阅读建议

告诉读者：

- 如果第一次接手，应先读什么
- 如果是改某类问题，应重点读什么

### 按问题找文档

如果一个目录下本身就有多类文档或多条阅读路径，不要只给线性顺序，还要告诉读者：

- 想理解主链看哪里
- 想理解专题设计看哪里
- 想理解未来路线看哪里
- 想核对代码边界时应该回到哪里

这类分流对 Codex 和第一次接手的人都很重要。

### 当前维护原则

对于文档型目录或设计型目录，建议额外写清楚：

- 哪些文档维护为当前真相
- 哪些文档只是专题说明
- 哪些文档不能替代当前实现
- 文档和代码冲突时以谁为准

### 何时更新本文件

每份模块文档都应回答：

- 哪些路径变化时，需要更新这份文档
- 哪类边界变化时，需要重写这份文档

## 不推荐的写法

- 不要把“目录罗列”当成“模块说明”。
- 不要直接把顶层目录名当成第一层文档层级，除非它本身就等于一个清晰的功能域。
- 不要只有路径，没有职责说明。
- 不要把“未来计划”写进“当前状态”正文。
- 不要在一份模块文档里试图解释整个项目。
- 不要复制代码实现细节来代替结构理解。
- 不要让 `package.json`、`tsconfig*`、构建配置主导项目文档叙事。

## 质量检查清单

写完一份文档后，至少检查这些问题：

- 一个第一次接手的人能否在 30 秒内知道这份文档讲什么
- Codex 能否从标题和前两段判断是否该继续读取
- 文档是否明确了边界，而不是泛泛而谈
- 文档是否告诉读者下一步该读哪里
- 文档是否仍然以“当前状态”为中心
